# Draft sections: benchmarking Methods and Results

Numbers are left as `XX` placeholders throughout. Every table and figure called out
here is generated by `jb2bench` and can be regenerated; the prose is written so that
it does not need to change when the numbers do.

---

## 2.11 Datasets

Benchmarking a genome browser needs a corpus that can be regenerated rather than
downloaded, both so that a reader can reproduce it and so that the same bytes can be
fed to every tool being compared. We therefore simulate alignments against a fixed
reference rather than using a public dataset.

The reference is a 250 kb slice of hg19 chr22, which we refer to throughout as the
contig `chr22_mask`. This is the same interval the 2023 JBrowse 2 paper simulated
against, and we reuse its generator invocations as well: short reads come from wgsim
and long reads from pbsim with the R103 error model. Reads are simulated at 20x, 200x
and 1000x coverage, giving six alignment cases (two read types by three coverages).
Each case is written as both BAM and CRAM from the same alignments, so the container
is an axis of the benchmark rather than a property of a particular file. BigWig
coverage tracks are generated at the same three coverages, and a separate panel of 100
per-sample BigWigs at 100 bp bins is generated for the cohort case described in §3.x.

Base modification data is a separate fixture. The long-read alignments are re-stamped
with CpG-context 5mC MM/ML tags by a seeded generator, so a modified-versus-plain
comparison differs by the tags and nothing else, and the tags are decoded back against
each read by an independent checker rather than trusted from the generator. We also
include one multi-group modBAM from real ONT data, because synthesized single-group
tags do not exercise the code path that a real basecaller's output does.

Two corpora sit outside this scheme and we mark them where they are used. The GFF3 and
VCF micro-benchmarks read their own generated corpora, because neither feature counts
nor sample counts fit inside a 19 kb alignment window. The CRAM-versus-samtools
reproduction additionally reads the corpus its original 2019 publication used, two
1000 Genomes NA12878 CRAMs against GRCh38, so that its published numbers can be
compared as published.

Unless stated otherwise, every measurement in this paper reads the window
`chr22_mask:124000-143000`, a 19 kb interval that matches the region used by JBrowse's
historical profiling harness.

One property of the simulated corpus is worth stating because it constrains what can
be measured on it. pbsim's long reads run off the ends of the contig, so long-read
depth tapers at both ends and any measurement that moves the view along the contig has
to avoid those windows. The pan benchmark described below runs leftward from the
benchmark locus and stops before the edge for this reason; a view that has drifted onto
thin data renders quickly for reasons that have nothing to do with the renderer.

## 2.12 Benchmark setup

### 2.12.1 What is measured

We report three families of measurement, and they answer different questions.

**End-to-end load** is the time from navigation to a completed first render, with a
cold application. It is the number a user would recognize as "how long until I can see
my data", and it is the one most often quoted for a genome browser. It is also the
least sensitive to the changes described in this paper, because it is dominated by
fetching and parsing, both of which happen in a web worker in either architecture, and
because it includes application boot and assembly resolution.

**Interaction** is the time from a zoom or a pan to correct content being on screen,
with the application already running. This is where the rendering architecture is
visible, and we consider it the more informative of the two.

**Per-frame cost** is the main-thread frame interval during a sustained gesture that
stays inside already-loaded data. It measures re-render and recompute rather than
either fetching or drawing, and we use it to attribute cost rather than to make
comparisons between tools.

Separately from the browser, we benchmark the parser packages directly, since they are
published independently of JBrowse and are used by other projects. Those results are
supplementary and are described in §S1.

### 2.12.2 Detecting that a render is finished

Every timing here reduces to the question of when a render is finished, and in our
experience the detector has been wrong more often than the thing being measured. We
therefore treat the detector as an instrument to be calibrated rather than a
convenience, and we implement three of them.

The first watches the application's own render-complete markers. This works within
JBrowse but not across its own history: releases up to 4.3.0 signal completion with
per-block `data-testid` attributes, while current main signals with display-level
phase and drawn attributes, and there is no overlap between the two. A detector that
knows only one contract finds nothing on a build using the other and times out. Our
implementation selects the contract inside the polling loop, since at the moment a page
is first navigated no display has mounted yet, and it records which contract it used so
that a row measured under one is not silently compared against a row measured under the
other.

The second polls screenshots and waits for the rendered pixels to stop changing. This
is the detector we use for cross-tool comparisons, because it belongs to neither tool:
igv.js hides its loading indicator when features finish loading rather than when they
finish drawing, so its own signal would credit it with a render it has not performed,
and JBrowse's indicator wording has changed between releases. The cost is that a
screenshot is not free. We measure it per harness, and it is large enough that this
detector has a floor in the hundreds of milliseconds. That floor is a small fraction of
a multi-second cold load and most of a pan, so we use paint quiescence for cold-load
comparisons and not for interaction comparisons.

The third patches the canvas drawing APIs and timestamps every call, reporting the last
draw before the page goes quiet. This asks the platform rather than the application,
and it costs an array push rather than a composite and an image encode. Draw
timestamps alone are not sufficient: JBrowse re-projects the reads it already holds
within a millisecond or two of a pan, then goes quiet while it fetches, then draws
again, so a detector watching only draws stops at the first gap and reports the
re-projection of stale content as the whole interaction. We therefore gate on network
activity as well, taken from the browser's debugging protocol rather than from a
patched `fetch`, since JBrowse fetches from a worker and a page-side hook would observe
igv.js's requests and none of JBrowse's.

We report the disagreement between these detectors rather than asserting that one is
correct (Table SX). The direction of the disagreement is not the obvious one: a draw
call precedes compositing, so draw timestamps ought to read early, and on a JBrowse
cold load they do not, because the application continues issuing draw calls after the
visible result has settled.

### 2.12.3 Controls

Several controls are applied to every comparison, and each of them exists because an
uncontrolled version of the measurement gave a wrong answer at some point during
development.

- **The build under test is resolved, not assumed.** Each runner fetches the served
  page, matches its content-hashed bundle against the set of staged builds, and labels
  the column with the build it actually found, aborting on an unrecognized one. Two
  runners had previously hardcoded different names for the same port.
- **Tools and builds are interleaved within a round.** Every arm of a comparison is
  measured back to back, so a transient on the measurement machine lands on all of them
  rather than on one column. This is what makes a ratio quotable on a machine whose
  absolute numbers are not.
- **Load is recorded per cell.** The one-minute load average is sampled either side of
  every measurement and reported with the row. We treat measurements taken above a
  fixed load ceiling as not comparable to measurements taken idle, and mark them as
  such rather than presenting a number that looks like a result.
- **Steps that did not do the work are excluded.** In the pan benchmark, JBrowse reads
  in 256 KiB blocks, so at low coverage a one-viewport pan can be served entirely from
  data already held. Those steps are counted and excluded from the headline, because
  averaging a cache hit together with a fetch and calling the difference "rendering" is
  the specific error the benchmark exists to avoid. A cache hit and a step the detector
  abandoned before the fetch began look identical in a request count, so they are
  separated by draw count: a real cache hit still shows a full render burst.
- **Where each tool actually landed is checked.** The two browsers are driven by
  different mechanisms — JBrowse by a scroll API and igv.js by a locus search — so the
  resulting position is compared and cases that disagree by more than 50 bp are
  reported as not comparable rather than as a comparison.
- **Equivalence is gated before timing.** For the parser benchmarks, a test asserts
  that the newer library returns every record the older one did within the query
  window, and the timings do not run if it fails. Records dropped at the window edge
  are distinguished from records dropped in the interior, since the two mean different
  things.

### 2.12.4 Rendering backends

The default backend ladder is WebGPU, then WebGL 2, then Canvas2D. The headline
measurements in this paper are taken on WebGL 2, pinned through a URL parameter, for
two reasons: it is the path the large majority of users reach today, and WebGPU on the
integrated GPU of our measurement machine initializes but emits texture allocation
validation errors and draws nothing. We report the backend comparison separately
(Table X), probing which backend each cell actually reached rather than assuming the
requested one, and measuring the fraction of each canvas that is not background so that
a cell which drew nothing is not reported as a fast render. WebGPU is measured through
Firefox Nightly for the same reason.

### 2.12.5 Environment and reproducibility

All measurements are taken on a single workstation and a pinned build of Chrome for
Testing, driven by Puppeteer. The browser version is pinned exactly rather than by
range, because the bundled browser is part of the instrument. Hardware rendering is
verified before each run rather than assumed, since a driver fallback to a software
rasterizer would silently turn a GPU benchmark into a CPU one.

The benchmark harness, the corpus generators and the raw results are available at
[repository URL], and every table in this section and the next is generated from the
recorded JSON rather than transcribed.

Two limitations follow from this setup and apply to everything below. The measurements
are from one machine at one locus, so they characterize an architecture rather than
predict a user's wall clock. And the server is `localhost`, which means that bytes cost
nothing to move; this understates every result that saves requests or bytes, and in
particular understates CRAM, whose entire trade is bytes on the wire against CPU at
read time.

## 3.x Performance

### 3.x.1 End-to-end load

Table X reports time from navigation to a completed first render for each corpus case
and each container, against the previous release and against the version described in
the 2023 paper.

This measurement is fetch-dominated. Both the old and the new architecture fetch and
parse in a web worker, and the number additionally includes application boot and
assembly resolution, so it undersells the rendering change; we report it because it is
the number a user recognizes, not because it isolates anything. The interaction
measurements below are where the architecture is visible.

Two properties of the table are worth reading before the numbers. First, the column
against version 2.4.0 is cumulative rather than a second isolation: three years
separate that release from the version described here and most of what changed in
between is not the renderer. The comparison against 4.3.0 is what isolates this work;
the comparison against 2.4.0 is what tells a reader of the previous paper what the
intervening period bought them. Second, part of the long-read improvement is not the
renderer at all, but the branch's SNP downsampling, which changes what is drawn rather
than only how fast it is drawn.

Cells that fail are reported as failures rather than dropped. A build that cannot
finish a case within the timeout is a result about that build.

### 3.x.2 Interaction

Interaction is measured three ways, and the three cases differ in whether either
architecture has to go back to the network.

**Zoom in** is the case where the new view is a strict subset of reads already held.
The GPU path re-projects what it has without a fetch, and the block-based renderer
re-renders and refetches. This is the new architecture's best case and Table X reports
it as such.

**Zoom out** was intended to be the case where both architectures must fetch, and it
largely does not work as a benchmark. Past a byte threshold JBrowse declines the fetch
and displays a message asking the user to zoom in or force the load. That path is fast
and paints nothing, so it initially scored as the best result in the table, which was a
refusal to draw. We report which cells drew and which refused, and take the median only
over cells that drew, but for anything heavier than the lightest case this comparison
contains no render timing and should not be read as one.

**Pan at constant zoom** is the measurement zoom-out was meant to be. One full viewport
sideways at fixed scale moves the view to a region neither architecture holds, and the
bytes per step are the same as the initial render's, so the density cap that turns
zoom-out into a refusal test is never approached. Both architectures pay the fetch, so
this is the hardest case for the new one and any remaining difference is render cost
rather than avoided network. Table X reports it, with the per-step request counts that
justify which steps are included.

Figure X shows the per-frame main-thread interval during a sustained gesture that stays
inside loaded data, under emulated CPU throttling. The result there is a negative one
about our own architecture and we state it plainly: frame time scales close to linearly
with the CPU throttle factor, which is the signature of a frame bound by main-thread
JavaScript rather than by the GPU. The GPU draw call does not appear among the
expensive frames and MobX reactivity is not among the top contributors. What does
appear is React reconciliation and CSS-in-JS serialization spread across the overlay and
chrome components that re-render on every interaction frame. At desktop speed there is
enough headroom that this is invisible; under any throttling it drops frames. The lever
this identifies is fewer React renders per frame and less style serialization per
render, not anything about the rendering backend, and we note it here because it is
where the next interaction improvement has to come from.

**Multiple tracks.** Table X reports the per-frame cost of a pan with several alignment
tracks open, which is the case the single-canvas-per-track design of the WebGL and
WebGPU backends is meant to address, and where the WebGL canvas-count limit described
in §2.4 becomes the binding constraint on how many tracks can be open at once.

### 3.x.3 Comparison against other browsers

Comparing genome browsers is harder than comparing libraries, because the tools differ
in more than the thing being measured, and we would rather state what a comparison
does and does not isolate than present a single headline ratio.

We compare against **igv.js**, which reads the same indexed BAM and CRAM files over
range requests from the same local server. Two architectural differences sit inside
every number: igv.js parses alignments on the main thread while JBrowse parses in a
worker, and JBrowse boots an application shell where igv.js mounts a widget. Both are
real differences between the tools rather than artifacts, but they mean a cold-load
comparison is measuring more than rendering. We therefore report the cross-tool
comparison as a pan (Table X), which holds scale fixed and runs against an application
that is already up, and report the cold load (Table SX) as supplementary.

Two controls are run alongside the igv.js arm. igv.js draws at most a configured number
of reads per 100 bp window, and JBrowse draws every read, so the comparison is repeated
with sampling raised to its maximum, which clips nothing on this corpus. igv.js also
packs rows until it runs out of canvas while JBrowse draws every read it holds and lets
the rasterizer clip, so a taller igv.js track is more igv.js work and no more JBrowse
work; the comparison is repeated at igv.js's own default track height and at the
height our harness gives it. Neither control moves the result, which is the point of
running them: the comparison is not one of a downsampled tool against a complete one.

Table X also reports canvas draw calls per step, which we consider the most robust
number in the comparison, since it is a function of the data and the code rather than
of the machine and repeats to within about one percent across runs. It is the
architectural difference in a single column, and it is worth being precise about what
it is not: it is not one draw call per read, and above a certain depth it stops growing
altogether. We report the magnitude and the saturation without asserting a cause,
because the obvious candidate — downsampling — is ruled out by the control above.

At the deepest long-read case igv.js does not complete. Diagnosed separately, its
renderer process reaches XX MB of heap and becomes ready only after XX s, before any
pan, and across repeated attempts it has timed out, closed its target, and completed
once. We report that cell as not reliably measurable at this depth rather than as a
large number.

**GenomeSpy** would be the more informative comparison of the two, and we were unable
to obtain it. GenomeSpy is WebGL 2 based and consumes the same `@gmod/bam` decoder that
JBrowse does, which means a comparison against it largely isolates the render path,
where igv.js confounds parser and renderer. Our harness loads GenomeSpy against the
same corpus and it draws nothing. Several candidate causes have been ruled out and the
remaining hypothesis concerns the interaction between its BAM source and an inline
genome definition, which our corpus requires because it is a synthetic contig. We
report this as an unresolved harness problem rather than as a result about GenomeSpy,
and note that a loss against it would be a more useful result to us than a win against
igv.js.

**HiGlass** with `higlass-pileup` reads client-side indexed BAM and would be a third
point of comparison; we have not built a harness for it. One thing can be said without
one: `higlass-pileup` pins a version of `@gmod/bam` six major versions behind current,
and the cost of that pin is measurable directly in the parser sweep (§S1) without a
HiGlass harness at all.

We note two comparisons that exist in the JBrowse project's own history and are not
re-run here: JBrowse 1, and the embedded React component packaging of JBrowse 2. Both
have harnesses in an older profiling repository, and their numbers are whole-process
wall-clock timings that include browser launch, so they are not commensurable with the
in-page measurements reported here and we do not quote them side by side.

### 3.x.4 Compute shaders

Table X compares the GPU and CPU implementations of the linkage-disequilibrium matrix
described in §2.7, across matrix sizes. The GPU timing is measured end to end — upload,
dispatch and readback — rather than as kernel time alone, since the transfer is part of
what the application pays.

Two practical notes come out of this. The work-unit threshold at which JBrowse switches
to the GPU path is conservative rather than a break-even point: measured at the
threshold itself the GPU path is still several times faster, so the crossover is below
it. And nothing currently bounds the high end, where kernel time grows quadratically in
the number of variants; because the GPU device is a singleton shared with the render
path, a driver reset would blank every GPU-backed track rather than only the matrix. We
observed a device loss once under sustained back-to-back dispatches and never from a
single dispatch, so we report the risk as bounded by measurement rather than as
characterized.

### 3.x.5 Parser and data-fetching results

The optimizations described in §2.1 are measured directly against the published
packages, at the versions JBrowse 2.4.0 resolved and at current releases, on the same
corpus and the same window as the render benchmarks. The full tables are supplementary
(§S1); we summarize here.

Two kinds of column appear in those tables and they do not decay together. Timings are
timings, and are subject to everything §2.12.3 says about the measurement machine.
Request counts and byte counts come from a filehandle that records every call: they are
exact, identical on every machine, and unaffected by load. We consider the second kind
more valuable than its prominence would suggest, because a read is a syscall locally
and a range request with a round trip over HTTP, and because it makes visible changes
that a timing cannot see. Three of these are worth stating in the main text:

- A change in `@gmod/cram` reduced the deep long-read query from XX reads over XX MB to
  XX reads over XX MB, at the same major version where the timing curve steps. Part of
  what reads as a decode speedup is a change in request shape.
- A change in `@gmod/bam` moved in the other direction on this corpus, issuing more
  requests and fetching more bytes while getting several times faster.
- Every version of `@gmod/bam` we measured retrieves the whole BAI index rather than
  ranging into it. This is invisible to a counter that watches only ranged reads, which
  is how it went unnoticed.

The BigWig case illustrates why a single-file benchmark can report nothing when there
is something to report. Answering a BigWig query means reading the header, walking the
chromosome B+ tree and descending the R-tree before any data is touched, and a
single-file measurement of that is a few milliseconds either way. A cohort panel pays
that cost once per sample and it does not amortize: reads per file is flat in the
number of files (Table SX). This is the shape of the workload behind the whole-genome
overview optimization described in §2.1.

## S1 Supplementary benchmarks

The following are reported in supplementary material rather than the main text. Each is
generated by the same harness and reads the same corpus except where noted.

**S1.1 Parser libraries, 2023 against current.** Two-point comparison of `@gmod/bam`,
`@gmod/cram`, `@gmod/bbi`, `@gmod/vcf` and `@gmod/bgzf-filehandle` at the versions
JBrowse 2.4.0 resolved and at current releases, built from source from pinned tags with
the same toolchain so that the difference is library code rather than a change of
transpiler target. Includes the record-equivalence gate and, for CRAM, a check of
derived reference spans against the BAM holding the same alignments.

**S1.2 Parser version sweep.** The same measurements across every major version line of
`@gmod/bam`, `@gmod/cram` and `@gmod/bbi`, which answers where along the way each
change arrived rather than only that it did. Includes the exact request and byte counts
described above.

**S1.3 Cohort BigWig panel.** Request shape and open time against number of files, for
a panel of 100 per-sample BigWigs.

**S1.4 GFF3 lazy attribute parsing.** Eager against lazy parsing of column 9, measured
both as a library and through the feature wrapper JBrowse actually uses, since the two
give different answers and only the second describes what a user sees. Includes
retained heap after parsing, which is a property of the result rather than a timing and
is the more durable half of the change for an adapter that holds an annotation resident
for the life of a session.

**S1.5 VCF genotype scan.** The genotype-scanning rewrite described in §2.1, across
sample counts and across two FORMAT shapes.

**S1.6 CRAM against samtools.** A reproduction of the benchmark published with
`@gmod/cram` in 2019, run on that paper's own corpus and on ours, against every major
version of the library since. The reproduction separates process startup from query
time, counts records per interval, and checksums the two tools' records against each
other, none of which the original did.

**S1.7 CRAM slice worker pool.** The effect of the configurable decompression worker
pool described in §2.1.

**S1.8 Rendering backend comparison.** WebGPU, WebGL 2 and Canvas2D on the same build
and the same case, with the reached backend probed per cell.

**S1.9 Cross-tool cold load.** The igv.js comparison including application boot, which
the pan comparison in §3.x.3 excludes.

**S1.10 Completion detector calibration.** The disagreement between the three detectors
described in §2.12.2, and the per-page cost of a screenshot that disqualifies paint
polling for interaction measurements.

**S1.11 Per-frame CPU profile.** The resolved profile behind Figure X, attributing
per-frame interaction cost to React reconciliation and CSS-in-JS serialization.
